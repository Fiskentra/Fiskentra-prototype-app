# Данные карты: G1–G4, F2/F4

Реализация в рабочей ветке карты; документ описывает изменения данных и локальные проверки, а не завершённую полевую приёмку.

## Хранилище и миграция

`PointLedger` хранит точки, receipt события, текущую revision, очередь операций и tombstone в одном versioned документе `files/map-data-v1.json`. Запись сначала попадает во временный файл, вызывает `FileDescriptor.sync`, затем атомарно заменяет документ. Android-адаптер также синхронизирует каталог. Состояние View берётся из кешированного snapshot; отрисовка не читает JSON. Завершённые операции сворачиваются в подтверждённую remote revision / tombstone, чтобы не накапливать копии фотографических метаданных при каждой правке.

Первая загрузка переносит старый `fiskentra_points.saved_points`; исходные preferences не очищаются и больше не перезаписываются новым PointStore. Точные исходные JSON точек, поездок и статусов дополнительно сохранены в `legacyBackup`. Атомарная публикация миграции допускает повтор после прерывания. ID, время, название, заметка, неизвестный type, символ/цвет/размер, weather, catch details и локальный путь фото сохранены. Архивные маршруты не преобразуются; исправлена потеря route при `FishingDayStore.stop()`. Операции разных экземпляров FishingDayStore синхронизированы. Геометрия TrackStore кешируется по исходному JSON; пауза/продолжение не меняют исходные точки и разрывы.

Новые поля SavedPoint: `eventId`, `tripId` (long, 0 — без привязки), `favorite`, `revision`, `locationState`, `locatedAtUtc`, `locationAccuracy`, `locationSource`. Все методы `with…` сохраняют остальные поля. Новые события получают поездку по времени возникновения; legacy — только при одном совпадении `[start,end)`. Для совпадающих интервалов привязка остаётся пустой. Редактор Details → Trip позволяет изменить её явно.

## Flic и записи без позиции

Single и double поступают в общий durable capture до сообщения об успехе. Без fix сохраняется та же запись с исходным UTC-временем и `hasLocation() == false`; JSON не содержит lat/lon. Journal и Saved показывают `Saved without location`. Карта/GPX/облачный координатный API не используют отсутствующую позицию. Ручные координаты или `Use current GPS position` с явным подтверждением прикрепляют положение и его время, не заменяя время события. Свежесть монотонная, автоматическая привязка ограничена fix рядом со временем события; будущие GPS callbacks не переписывают запись.

Flic 2 SDK сообщает timestamp в миллисекундах от запуска кнопки; UTC оценивается через callback ready. Идентичность включает кнопку, персистентную эпоху, timestamp и действие. Перезапуск приложения/обычный reconnect сохраняет эпоху; регресс uptime кнопки создаёт новую. Изменение часов телефона не меняет идентичность. В API используемой версии нет публичного boot ID: сценарий замены батареи с новым uptime, превышающим последний наблюдавшийся uptime, требует отдельного аппаратного испытания. Два разных намеренных события не объединяются по типу/координатам/календарному времени.

Hold записывает receipt события и переход IDLE/RECORDING/PAUSED одним `SharedPreferences.commit`, не ждёт GPS и не добавляет точку. Повторный hold callback не переключает запись второй раз. Capture/hold фонового сервиса выполняются последовательно вне UI. Weather — необязательное обогащение: не меняет время события и не отменяет факт уже успешной durable записи.

## Удаление и очередь

PointStore insert/edit уже сохраняют соответствующую операцию в той же транзакции. UI `enqueue` только запускает worker; поздний callback со старым объектом не может создать запись. Delete сначала сохраняет tombstone и убирает видимую точку, затем сообщает об успешном локальном удалении. Никогда не отправленная запись удаляется без HTTP. Удаление во время upsert ждёт его результата; после рестарта незавершённый запрос повторяется с тем же operationId до следующей операции этого ID. Старые DELETE_FAILED/DELETING мигрируют в удаления, а не в новые upsert.

Сеть/429/5xx используют ограниченный backoff 5 секунд–15 минут. Ошибки доступа и постоянные ошибки остаются видны; Retry доступен через существующую синхронизацию и карточку. HTTP 409 не считается успехом. DELETE с нулём представленных строк не доказывает наличие прав и оставляет ошибку доступа; локальная запись при этом остаётся удалённой. Повтор уже подтверждённого локального удаления не требует нового запроса. Изменений production-схемы/RLS нет.

Статус текущей точки использует именно её revision. Успех предыдущей revision не подтверждает более новую правку. Даже подтверждённая загрузка обозначена `Coordinates synced · details on this device`. Пустая очередь не обещает backup фотографий, оформления, избранного и треков.

Фото в существующих Journal/Saved/редакторе также декодируются вне главного потока через `LocalCatchPhoto`: два worker, уменьшение изображения, ограниченный кеш 6 МБ и отмена/отбрасывание результата после detach. Недоступная фотография не мешает остальным данным записи.
